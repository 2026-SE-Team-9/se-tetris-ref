# 프로젝트 및 협업 규칙

> 이 문서는 팀의 **작업 흐름과 규칙에 대한 기준 문서**다.
> PR 리뷰 agent의 프롬프트를 포함해 다른 곳에 같은 규칙이 적혀 있다면, 이 문서를 따른다.
> 규칙을 바꿀 때는 **이 문서와 agent 프롬프트를 함께** 수정한다.

---

## 1. 프로젝트 정의

이 프로젝트는 서울과학기술대학교 소프트웨어공학 팀 프로젝트로 진행하는 Java Swing 기반 테트리스 애플리케이션입니다.

- 요구사항 기준: `docs/TeamProject_Req1.pdf`, `docs/requirements-1.md` 및 이후 차수 요구사항 문서
- 작업 계획과 진행 상태: Jira `TET` 프로젝트, GitHub Issue에는 요약과 Jira 링크 기록
- 구현 내용과 검증 결과: GitHub Pull Request
- 기본 개발 브랜치: `dev`
- 배포 및 최종 통합 브랜치: `main`

Jira에는 작업의 목적, 범위와 완료 조건을 기록하고, PR에는 실제 구현 내용, 변경 파일과 검증 결과를 기록합니다.

### 도구 역할

| 도구 | 담당 |
| :--- | :--- |
| **Jira** | 이슈(할 일) 관리, 담당자 지정, 진행 상태 |
| **GitHub** | Jira 이슈 요약, 코드, 브랜치, PR, 리뷰 |

Jira 이슈에 대응하는 GitHub Issue를 만들어 작업과 해결 내역을 GitHub에서도 추적합니다. 상세 내용과 진행 상태의 기준은 Jira이며, GitHub Projects는 사용하지 않습니다.
GitHub Issue는 `.github/github_issue_template.md`의 본문을 사용해 배경, 할 일과 완료 기준을 간단히 기록합니다. Jira 이슈에 대응할 때는 세 항목을 Jira 내용으로 요약하고 `관련 링크`에 Jira URL을 넣어 4줄로 작성합니다. 담당자가 확인되면 담당 1줄을 추가합니다. 같은 Jira Key의 GitHub Issue가 이미 있는지 먼저 확인하여 중복 생성하지 않습니다.

## 2. Git 컨벤션

### 브랜치 전략

```text
feat/TET-12-...  ─┐
fix/TET-15-...   ─┼─▶  dev  ──(차수 제출 시점)──▶  main
docs/TET-18-...  ─┘
```

| 브랜치 | 역할 |
| :--- | :--- |
| **`dev`** | 기본 브랜치. 평소 모든 작업이 여기로 모입니다 |
| **`main`** | 제출 가능한 안정 버전. 차수별 제출 시점에만 `dev`에서 병합 |
| 작업 브랜치 | 이슈 하나당 하나. 병합 후 삭제 |

- `main`과 `dev`에는 직접 push하지 않습니다.
- 일반 작업 PR은 `dev`를 대상으로 생성합니다.
- `dev`에서 `main`으로의 통합은 별도로 결정하고 수동으로 진행합니다.
- 서로 독립적인 작업은 Jira 이슈, GitHub Issue, 브랜치와 PR을 각각 분리합니다.

**작업 브랜치는 항상 `dev`에서 딴다.** `main`에서 따면 오래된 코드 기준으로 작업하게 됩니다.

### 보호 설정

`main`과 `dev`에는 룰셋이 적용되어 있습니다.

- 직접 push 불가 — 모든 변경은 PR을 거칩니다
- 병합하려면 **승인 1명 이상** 필요
- 강제 push(force push) 차단
- 브랜치 삭제 차단

> 팀원 전원이 Organization Owner라 룰셋을 끌 수 있는 권한이 있습니다.
> **임의로 끄지 않습니다.** 필요한 상황이 생기면 팀에 먼저 알립니다.

### 브랜치 이름

```text
<type>/<Jira-Key>-<kebab-case-작업명>
```

예시:

```text
feat/TET-12-colorblind-mode
fix/TET-13-rotation-collision
docs/TET-14-update-requirements
```

| 유형 | 사용 기준 |
| :--- | :--- |
| `feat` | 새로운 기능 |
| `fix` | 오류 수정 |
| `refactor` | 동작을 바꾸지 않는 구조 개선 |
| `test` | 테스트 추가 및 수정 |
| `docs` | 문서 작성 및 수정 |
| `chore` | 빌드, 설정, CI 및 협업 환경 정비 |

고민될 때는 `chore`를 사용합니다. 유형 선택에 시간을 쓰지 않습니다.

### 커밋과 PR 제목

```text
[<Jira-Key>] <type>: <설명>
```

예시:

```text
[TET-12] feat: 색맹 모드 렌더링 추가
[TET-15] fix: 벽에 붙은 상태에서 회전 시 겹침 수정
[TET-12] test: 메뉴 이동 단위 테스트 추가
```

- 커밋은 하나의 목적을 갖도록 원자적으로 작성합니다.
- 브랜치 유형, 커밋 유형과 PR 제목 유형을 일치시킵니다.
- PR 본문과 AI 코드 리뷰 댓글은 분리합니다.
- PR 브랜치를 push한 경우 최신 HEAD 전체 diff를 다시 검토합니다.

### Jira Key 표기

Jira 이슈마다 `TET-12` 같은 Key가 붙습니다. 브랜치, 커밋과 PR 제목에는 이 Key를 넣고, 대응 GitHub Issue와 PR 본문에는 Jira 링크를 적습니다.

**브랜치 이름, 커밋 메시지, PR 제목 세 곳에 모두 넣습니다.**
하나만 넣어도 연결은 되지만, 빠뜨린 항목은 Jira에서 보이지 않습니다.

> Key는 **대문자**여야 합니다. `tet-12`는 인식되지 않습니다.

### 금지 사항

| 명령 | 이유 |
| :--- | :--- |
| `git push --force` | 원격 이력을 덮어써 **팀원 커밋이 사라질 수 있습니다** |
| `git reset --hard` | 로컬 변경을 복구 불가능하게 날립니다 |
| `git rebase` | 커밋을 새로 만들어 이력이 어긋납니다 |

세 가지 모두 "이력을 고쳐 쓰는" 계열입니다. **덧붙이기만 하면 최악의 경우에도 복구됩니다.**

> ⚠️ **TortoiseGit 사용 시 주의**
> Push 창에 **`Force: May discard known changes`** 체크박스가 있습니다.
> Push가 거부되었을 때 눈에 들어오지만, **절대 체크하지 않습니다.**
> Push 거부의 올바른 대응은 Force가 아니라 **Pull 먼저**입니다.

## 3. Pull Request

### 작성

- **대상 브랜치는 `dev`** (차수 제출 시점의 `dev` → `main` 병합만 예외)
- 제목은 `[<Jira-Key>] <type>: <설명>` 형식
- 설명은 `.github/pull_request_template.md` 양식으로 작성합니다. 무엇을, 왜 바꿨는지와 검증 결과, Jira 완료 조건 체크리스트, Jira 링크와 GitHub Issue 번호를 포함합니다. 해결하는 PR은 `Closes #<번호>`로 연결합니다
- 리뷰어를 지정합니다. 지정은 자신을 제외한 전원으로 합니다

### 리뷰

리뷰할 때 볼 것 세 가지:

1. 요구사항대로 동작하는가
2. 다른 사람 코드를 망가뜨리지 않는가
3. 테스트가 있는가

코드 스타일 지적은 최소한으로 합니다. 사람 리뷰는 설계 판단에 씁니다.

> 리뷰 코멘트는 그 자체로 **"논의 사항 기록" 산출물**이 됩니다.
> 짧아도 좋으니 코멘트를 남기는 습관을 들입니다.

### 병합

- 승인 1명 이상 필요
- 병합 방식은 **Squash and Merge 사용** (Rebase는 비활성화됨)
- 병합 후 작업 브랜치 삭제 (원격 브랜치는 병합 시 자동 삭제됨)

## 4. Jira 컨벤션

### 제목과 설명

Jira 제목은 상태가 아니라 달성하려는 결과를 표현합니다.

```text
<type>: <작업 내용을 나타내는 간결한 제목>
```

`메뉴 작업 중` 대신 `feat: 색맹 모드 메뉴 구현`처럼 작성합니다. 진행 여부는 Jira 상태로 관리합니다.

설명에는 다음 내용을 포함합니다.

- 배경 및 목적
- 작업 범위와 제외 범위
- 완료 조건
- 검증 방법
- 의존 이슈와 제약사항

### 이슈 유형

| 유형 | 사용 기준 |
| :--- | :--- |
| 에픽 | 여러 스토리와 작업을 포함하는 큰 목표 |
| 스토리 | 사용자가 체감할 수 있는 기능 |
| 작업 | 문서, 설정, 리팩터링, 테스트, CI 및 협업 규칙 |
| Subtask | 하나의 상위 이슈를 구현 가능한 단위로 분리 |
| 버그 | 오류 수정. 프로젝트에 유형이 없으면 `작업`과 `bug` 레이블을 사용 |

에픽은 단일 문서 작성이나 작은 설정 변경에 사용하지 않습니다. 하나의 이슈가 며칠 안에 끝내기 어렵거나 여러 독립 결과를 포함하면 하위 스토리 또는 작업으로 나눕니다.

### 우선순위와 기한

| 우선순위 | 사용 기준 |
| :--- | :--- |
| Highest | 마감이 임박했거나 전체 작업을 차단함 |
| High | 이번 주 반드시 완료해야 함 |
| Medium | 일반적인 작업 |
| Low | 여유가 있을 때 처리 가능 |

- 모든 이슈를 `Medium`으로 두지 않고 실제 처리 순서를 반영합니다.
- 기한은 제출일, 발표일, 외부 의존성 등 실제 마감이 있는 작업에만 설정합니다.
- 일반 작업의 순서는 백로그의 Rank로 관리합니다.
- **각 이슈에는 책임 담당자 한 명을 지정합니다.** 담당자 없는 이슈는 아무도 하지 않는 일이 됩니다.
- 이슈 크기는 **1~3일 분량**으로 쪼갭니다. 너무 크면 몇 주째 `진행 중`에 멈춰 있게 됩니다.
- 회의에서 정한 할 일은 **바로 이슈로 만듭니다.**

### 백로그와 칸반 보드

이 프로젝트는 별도 백로그가 활성화된 칸반 방식으로 운영합니다.

Jira의 백로그 화면에는 `Backlog` 영역과 `Board` 영역이 함께 표시됩니다. 이 두 영역은 작업을 현재 칸반 보드에 올릴지 결정하는 **계획 위치**이고, 실제 보드의 `해야 할 일`, `진행 중`, `검토 중`, `완료`는 작업의 **진행 상태**입니다.

| 백로그 화면의 영역 | 기준 |
| :--- | :--- |
| Backlog | 향후 수행할 작업 후보. 요구사항이나 우선순위를 더 정리해야 하거나 아직 착수할 필요가 없음 |
| Board | 현재 칸반 보드에서 처리하기로 선택한 작업. 실제 보드에 표시됨 |

Board 영역에 올린 이슈는 실제 칸반 보드에서 다음 상태로 관리합니다.

| 실제 보드 상태 | 기준 |
| :--- | :--- |
| 해야 할 일 | 범위와 완료 조건이 정리되어 바로 시작할 수 있음 |
| 진행 중 | 담당자가 브랜치를 생성하고 작업 중 |
| 검토 중 | PR이 생성되어 검토 중 |
| 완료 | PR 병합 및 완료 조건 확인 완료 |

```text
Backlog 영역: 향후 작업 후보
       ↓ 범위와 완료 조건 정리
Board 영역 / 해야 할 일: 현재 처리 대상으로 선택했지만 아직 미착수
       ↓ 브랜치 생성 및 작업 시작
진행 중 → 검토 중 → 완료
```

- 새 이슈는 기본적으로 Backlog에 둡니다.
- 다음에 수행할 이슈가 위에 오도록 Rank를 정리합니다.
- 작업 준비가 끝난 이슈만 백로그 화면의 `Board` 영역으로 옮깁니다. 이 이슈는 실제 보드의 `해야 할 일`에 표시됩니다.
- 한 사람이 동시에 진행하는 이슈는 원칙적으로 1개로 제한합니다.
- `검토 중` 작업은 팀 전체 2개 이하를 권장합니다.

### 이슈 재사용과 범위 변경

- 완료되거나 취소된 이슈는 명시적으로 재오픈하지 않는 한 재사용하지 않습니다.
- 같은 목표의 작은 변경은 기존 이슈의 작업 범위 또는 완료 조건을 보완합니다.
- 독립적인 변경은 새 Jira 이슈와 별도 브랜치/PR로 분리합니다.
- 실제 작업이 Jira 이슈와 관련 없으면 커밋 전에 중단하고 올바른 이슈를 선택합니다.

### 개발 정보 확인

Jira 이슈 화면 오른쪽 **개발(Development)** 영역에서 연결된 브랜치·커밋·PR을 볼 수 있습니다.

> **반영에 시간이 걸립니다.** push 직후에는 표시되지 않고, 몇 분에서 수십 분 뒤에 나타납니다.
> 바로 안 보인다고 해서 연결이 실패한 것은 아닙니다.

### 이슈 생성과 보완

새 이슈를 만들거나 기존 이슈를 보완할 때는 **`.github/jira_issue_template.md` 절차**를 따릅니다.

1. 관련된 기존 이슈를 먼저 검색합니다. 재사용하거나 보완할 이슈가 있으면 새로 만들지 않습니다.
2. 제목과 설명을 템플릿의 형식(배경 및 목적, 작업 범위, 제외 범위, 완료 조건, 검증 방법, 참고사항)으로 작성합니다.
3. 생성하거나 수정하기 전에 초안 내용을 확인하고 승인한 뒤 반영합니다.

완료 조건은 결과로 확인할 수 있는 항목만 2~4개 작성합니다. 이 완료 조건은 PR 본문의 체크리스트로 그대로 옮겨져 검증 기준이 됩니다.

## 5. 작업 흐름

1. Backlog에서 우선순위가 높은 이슈의 담당자, 작업 범위와 완료 조건을 정리합니다.
2. 바로 시작할 수 있는 이슈를 보드의 `해야 할 일`로 옮깁니다.
3. 실제 작업을 시작할 때 `진행 중`으로 옮기고, `dev`에서 Jira Key가 포함된 브랜치를 생성합니다.
4. 같은 Jira Key의 GitHub Issue가 있는지 확인하고, 없으면 Jira 내용을 4~5줄로 요약해 링크와 함께 등록합니다.
5. 작업 중 범위가 달라지면 Jira 이슈와 전체 diff의 정합성을 다시 확인합니다.
6. `dev` 대상 PR에 Jira 링크와 GitHub Issue 번호를 함께 적습니다. PR이 해당 작업을 해결하면 `Closes #<번호>`로 연결하고 Jira 이슈를 `검토 중`으로 옮깁니다.
7. PR 병합 후 GitHub Issue 종료 여부와 Jira 완료 조건을 확인하고 Jira 이슈를 `완료`로 옮깁니다.
8. 로컬에서 `dev`로 전환한 뒤 작업 브랜치를 삭제하고 Pull 합니다.

8번을 빼먹으면 다음 브랜치를 오래된 기준에서 따게 됩니다.

브랜치, 커밋과 PR에 Jira Key를 포함하면 개발 정보가 연결될 수 있지만, 상태 자동 전환은 별도의 Jira 자동화 설정이 필요할 수 있습니다.

## 6. 자주 겪는 상황

### Push가 거부될 때

원격에 내가 모르는 변경이 있다는 뜻입니다.
**Force가 아니라 Pull을 먼저 합니다.** 충돌이 나면 아래 항목대로 해결합니다.

### 충돌이 났을 때

주로 같은 파일의 같은 줄을 두 사람이 다르게 고쳤을 때 발생합니다.

1. 충돌 파일 우클릭 → `Edit conflicts` (TortoiseGitMerge가 열림)
2. 좌/우 중 어느 쪽을 쓸지 선택하거나 직접 편집
3. 우클릭 → `Resolved` → 커밋

직접 편집하는 경우 `<<<<<<<`, `=======`, `>>>>>>>` 표시줄을 **전부 지웁니다.**

### Jira Key를 빠뜨렸을 때

이미 push한 커밋 메시지는 고치지 않습니다(이력이 바뀝니다).
**PR 제목에 Key를 넣으면** 그 PR을 통해 연결됩니다.

### 뭔가 잘못된 것 같을 때

작업 폴더를 통째로 복사해두고 시작합니다. 원시적이지만 확실합니다.

## 8. 계층 규칙

구현 시 반드시 지킵니다. 이 규칙이 깨지면 테스트 커버리지 요건과 색맹 모드·화면 크기 조절이 동시에 어려워집니다.

### 규칙

1. **모델은 `javax.swing`을 import하지 않는다**
2. **모델은 색을 모른다** — 색 결정은 팔레트의 일
3. **모델은 설정을 모른다** — 화면 크기·키 설정은 모델 바깥의 일

### 적용 범위

아래 패키지의 코드를 모델로 보고 위 규칙을 적용합니다. 경로는 `tetris/src/main/java/seoultech/se/tetris/` 기준입니다.

| 패키지 | 내용 |
| :--- | :--- |
| `blocks/` | 블럭 종류와 블럭 상태 |
| `engine/` | 보드와 게임 진행 로직 |
| `component/model/` | 모델 인터페이스 (`GameState`) |

`legacy/`는 참조 코드이므로 적용 대상이 아닙니다.
