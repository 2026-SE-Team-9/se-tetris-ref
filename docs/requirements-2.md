**아이템 모드 추가**

- 2차 요구사항의 목표는 아이템 모드의 추가이며, 일반 모드의 일부 수정을 포함한다

# 세부 요구사항

## 난이도

- 일반 게임 모드에 난이도 설정을 추가한다 — **쉬움 / 중간 / 어려움** 3단계
- 쉬움에서는 I형 블럭이 20% 더, 어려움에서는 20% 덜 등장한다
  - 다른 블럭의 가중치를 10이라 하면 I형 블럭은 쉬움 **12**, 어려움 **8**
- 줄 삭제에 따른 속도 증가는 쉬움에서 20% 적게, 어려움에서 20% 많게 한다
- 그 외 난이도에 따른 규칙이나 점수는 자유
- 스코어보드에서 각 기록이 어떤 난이도의 기록인지 확인할 수 있어야 한다
- 난이도는 **설정에서** 선택한다

> 📌 **팀 결정**
> - 난이도는 **일반 모드와 아이템 모드에 모두** 적용한다
> - 설정 파일에 난이도가 없으면 **중간**을 기본값으로 한다
> - 가중치 기준으로 구현한다. 쉬움에서 I형 블럭의 실제 확률은 10/70 → 12/72 (약 1.17배)가 된다
> - **속도 증가:** 1차의 낙하 간격 공식(레벨마다 이전 간격 × 0.8, 하한 100ms)에서 곱하는 비율을 난이도에 따라 바꾼다
>
> | 난이도 | 레벨당 간격 비율 | 레벨당 감소폭 |
> |---|---|---|
> | 쉬움 | 0.84 | 16% (20% 적게) |
> | 중간 | 0.80 | 20% |
> | 어려움 | 0.76 | 24% (20% 많게) |

## 줄 삭제 애니메이션

- 삭제되는 줄을 시각적으로 구분할 수 있도록 삭제 애니메이션을 추가한다
  - 예: 하얀색으로 한 번 반짝이고 삭제

> 📌 **팀 결정**
> - 게임 로직에 삭제 애니메이션용 상태를 추가한다. 애니메이션 동안 게임 진행을 멈추고, 애니메이션이 끝나면 다시 진행한다
> - 애니메이션으로 멈춘 동안에는 **입력을 받지 않는다** (일시정지 키 포함)
> - 사용자의 일시정지와는 **별개의 상태**로 둔다. 같은 상태를 쓰면 애니메이션 도중 일시정지 메뉴가 뜨거나 해제 키로 애니메이션을 건너뛰게 된다
> - 애니메이션 길이는 낙하 타이머가 아닌 **고정 길이 타이머**로 잰다. 낙하 간격은 레벨마다 달라지기 때문이다
> - 일반 줄 삭제뿐 아니라 **아이템이 칸·줄을 지우는 동작에도 같은 방식**을 적용한다

## 확률에 따른 블럭 생성

- 난이도에 따른 블럭 생성을 위해 블럭마다 생성 확률을 다르게 처리할 수 있어야 한다
  - Roulette Wheel Selection 같은 방식을 활용할 수 있다 (참고 자료: e-class `rws.pdf`)
- 블럭이 요구사항의 확률로 생성되는지 확인하는 **단위 테스트**를 추가한다
  - 최소 **1,000회** 이상 선택했을 때 블럭 분포가 실제 확률 대비 **±5%** 이내인지 검증
  - **실제 게임에서 사용하는 코드**가 테스트를 통과해야 한다
  - 예: 블럭 4개 중 B의 확률을 2배로 하면 B는 40%, 나머지는 각각 20%. 1,000번 반복하면 B는 약 400개, 나머지는 약 200개
  - 코드에 문제가 없는데 오차가 예상보다 크다면 시행 횟수를 늘릴 수 있다

> 📌 **팀 결정**
> - **시행 횟수 10만 회, 상대 오차 ±5%** 를 기준으로 한다
>   - 시행 횟수를 충분히 크게 잡아 오차로 인한 실패의 가능성을 줄인다
>   - 오차가 상대 오차와 절대 오차 중 어느 쪽인지에 대한 부분은 명시되어 있지 않았는데, 상대 오차를 적용한 수치가 절대 오차보다 더 작으므로 상대 오차를 기준으로 한다
> - 실제 게임에서 쓰는 `BlockFactory`를 그대로 테스트하며, `Random`을 주입해 결과를 재현할 수 있게 한다

## 아이템 등장

- **10줄**을 삭제할 때마다 아이템이 등장한다
- 아이템은 기존 블럭에 섞여서 나오거나, 블럭 자체가 아이템일 수 있다
- 10줄 삭제 시 다음 블럭 표시 영역에 새로 나타나는 블럭은 아이템이거나 아이템을 포함하는 블럭이어야 한다
- 아이템은 모양이 특징적이거나 기본 블럭과 다른 문자로 표시하며, **아이템끼리도 서로 다른 문자**를 사용한다
- 원문 제시 아이템 2개 외에 팀에서 **최소 3개 이상**의 아이템을 추가해야 한다

> 📌 **팀 결정**
> - 10줄 삭제를 채운 블럭의 **다다음 블럭**이 아이템 블럭이 된다 (이미 다음 블럭 영역에 표시 중인 블럭은 바꾸지 않는다)
> - 여러 줄을 지워 10줄 단위를 넘긴 경우에도 아이템이 등장한다 (예: 9줄 → 12줄)
> - 줄 삭제 아이템으로 지운 줄은 10줄 카운트에 **포함**한다. 무게추·Tall Boy·Crusher로 지운 칸·줄은 **포함하지 않는다**
> - 아이템 5종 중 **균등한 확률**로 선택한다

## 줄 삭제 아이템

- 기본 블럭 안에 포함되는 아이템으로, 문자 **`L`** 로 표시한다
- 블럭이 고정되면 줄이 꽉 찼는지와 관계없이 `L`이 포함된 줄을 바로 삭제한다
- 아이템이 블럭에 붙는 위치는 무작위
  - 예: I형 블럭이면 `OOOL`, `OOLO`, `OLOO`, `LOOO` 중 하나
- 아이템으로 사라지는 줄의 점수는 기존 방식과 동일하게 계산한다

> 📌 **팀 결정**
> - `L`이 있는 줄이 동시에 꽉 찬 줄이면 **일반 줄 삭제로 처리**한다 (중복 계산하지 않음)
> - 점수는 `L` 줄과 꽉 찬 줄을 합친 **총 삭제 줄 수**로 계산한다
> - `L`은 블럭이 회전해도 같은 칸에 붙어 있다
> - 고정 즉시 삭제되므로 보드에 `L`이 남지 않는다
> - 블럭 하드 드롭은 일반 블럭과 같다

## 무게추 아이템

- 너비 **4칸**의 아이템. 형태와 표시 문자는 너비 4칸을 만족하는 선에서 자유
  - 예시 형태: 위 2칸, 아래 4칸
- 떨어지면서 아래의 모든 블럭을 제거한다
- 처음에는 좌우로 움직일 수 있으나, 고정된 상태가 되면 좌우로 움직일 수 없다
- 아이템 사용이나 지워지는 블럭에 대한 점수는 기본적으로 없으나, 아이템과 관련된 점수 규칙을 추가할 수 있다

> 📌 **팀 결정**
> - 원문 예시 형태를 사용하고, 문자 **`A`** 로 표시한다. 아이템은 회전하지 않는다
> - 바닥이나 블럭에 닿으면 좌우 이동이 막히고, **게임을 멈춘 상태에서** 아래 칸을 바닥까지 제거한다 (줄 삭제 애니메이션과 같은 방식)
> - 바닥에 착지한 무게추는 **보드에 그대로 남으며**, 이후 일반 블럭처럼 줄 삭제 대상이 된다
> - 점수: **제거한 칸 수 × 10점**, 레벨 배율 적용
>   - 1줄 삭제(10칸 100점)와 같은 칸당 단가다. 4줄 삭제(칸당 25점)보다 낮아 줄 삭제보다 유리해지지 않는다
> - 줄 삭제가 아니므로 10줄 카운트와 백투백에 영향을 주지 않는다
> - 빈 보드에 떨어지면 제거 없이 바닥에 착지하고 0점이다
> - 하드 드롭하면 착지 지점부터 동일하게 제거 동작을 한다

## 추가 아이템

> 📌 **팀 결정**
> 원문 요구에 따라 팀에서 설계한 아이템 3종이다. 평가 팀이 이 명세만 보고 동작을 확인할 수 있도록 작성한다.
> 아이템이 칸·줄을 지우는 동작은 모두 줄 삭제 애니메이션과 같은 방식으로 게임을 멈춘 뒤 처리한다.

### Double or Nothing (`D`)

줄 삭제로 지우면 점수가 2배(Double), 다른 아이템에 지워지면 효과가 없는(Nothing) 아이템

- 기본 블럭 안에 포함되며, 붙는 위치는 무작위다. 블럭이 회전해도 같은 칸에 붙어 있다
- 고정된 뒤 **그 줄이 지워질 때까지 보드에 남는다**. 아래 줄이 지워지면 함께 내려온다
- `D`가 있는 줄이 **꽉 찬 줄로 삭제되면**, 그 줄 삭제의 **최종 점수**(레벨 배율·백투백 적용 후)를 **2배**로 한다
- 한 번의 줄 삭제에 `D`가 여러 개 있어도 2배는 **한 번만** 적용한다
- 줄 삭제 아이템·무게추·Tall Boy·Crusher에 지워지면 **가산 없이 사라진다**
  - 단, 그 줄이 꽉 찬 줄이기도 하면 일반 줄 삭제가 우선하므로 2배를 적용한다

### Tall Boy (`B`)

땅속으로 파고들어 주변을 날려버리는 아이템

- **1×1** 크기의 독립형 아이템이다
- 보드에 고정되면 자신 아래로 **2칸 파고든 뒤**, 자신을 중심으로 **5×5** 범위의 블럭을 제거한다
  - 파고드는 2칸은 5×5 범위 안에 포함된다
  - 바닥까지 2칸이 남지 않으면 파고들 수 있는 만큼만 내려간다
  - 5×5 범위 중 보드 안쪽만 제거한다
- 폭발과 함께 자신도 사라진다
- 제거된 칸 위의 블럭은 떨어지지 않고 그대로 남는다
- 점수: **블럭이 있던 칸 수 × 10점** (빈 칸은 0점), 레벨 배율 적용
  - 자신의 칸도 포함한다 (자신도 사라지는 아이템이기 때문). 최대 250점
- 줄 삭제가 아니므로 10줄 카운트와 백투백에 영향을 주지 않는다

### Crusher (`C`)

아래쪽 줄을 짓눌러 없애는 아이템

- **3×3** 크기의 사각형 모양을 가진 독립형 아이템이다
- 보드에 고정되면 자신 아래에 있는 줄들을 **보드 맨 아래부터 최대 3줄까지** 통째로 삭제한다
  - 삭제한 줄 수만큼 위의 줄들(자신 포함)이 내려온다
  - 자신보다 아래에 있는 줄이 3줄 미만이면 그 줄들만 삭제한다. 바닥에 닿아 있으면 삭제할 줄이 없다
- 자신은 무게추처럼 **보드에 남으며**, 이후 일반 블럭처럼 줄 삭제 대상이 된다
- 점수는 없다
- **줄 삭제로 보지 않는다** — 10줄 카운트와 백투백에 영향을 주지 않는다

## 아이템 모드 관련 추가사항

- 아이템을 추가하는 것을 어렵지 않게 수행할 수 있는 구조로 설계한다
- 명시된 요구사항 외의 규칙은 1차 요구사항과 충돌하지 않도록 설계한다
  - 예: 아이템 표시 + 색맹 모드, 난이도 설정 저장, 게임 실행 환경
- 팀에서 설계·구현한 아이템은 형태와 기능을 요구사항이나 명세서 형태로 정리하여 평가 시 확인 자료로 제공한다

> 📌 **팀 결정**
> - 아이템은 공통 인터페이스로 구현하고, 엔진은 정해진 시점(고정 시, 줄 삭제 시, 좌우 이동 가능 여부 판단 등)에 아이템을 호출한다
> - 아이템의 효과는 보드가 아니라 **게임 문맥 객체**를 받아 수행한다
> - 무게추·Crusher·`D`처럼 **보드에 남는 아이템**을 표현하기 위해 보드의 칸 정보를 확장한다
> - **1차 기능과의 관계**
>   - 색맹 모드: 모든 아이템이 고유 문자를 가지므로 색과 무관하게 구분된다
>   - 화면 크기: 아이템 문자도 칸 크기에 맞춰 표시한다
>   - 설정 저장: 난이도를 설정 파일에 저장하며, 설정 초기화 시 중간으로 돌아간다
>   - 게임 종료: 아이템 블럭이 생성 위치에 놓일 수 없으면 기존과 같이 게임 종료. 애니메이션 도중 게임 종료 조건이 생기면 애니메이션을 마친 뒤 종료한다

## 고스트 블럭

1차 문서의 추가 세부사항. 현재 블럭이 떨어질 위치를 미리 표시한다.

> 📌 **팀 결정**
> - 표시 문자는 **`#`** 로 하며, 실제 블럭과 구분되도록 흐리게 표시한다
> - 무게추의 고스트는 처음 닿는 위치에 표시한다 (그 지점에서 멈추고 제거가 시작되므로)
> - 애니메이션 도중에는 표시하지 않는다

# 개발 및 운영

## 프로젝트 관리

- 프로젝트 진척 상황과 Task 배정 내역 등을 적절한 도구(예: Trello)로 관리하고, 팀원의 생산성을 확인할 수 있어야 한다
- 코드와 필요한 자료는 Git과 GitHub 저장소로 관리하며, Branch 관리나 Pull Request 처리 정책 등 버전 관리가 이루어져야 한다
- 프로젝트 진행 중 발생하는 이슈는 **GitHub에 이슈로 등록**하고 해결 내역을 추적할 수 있어야 한다

> 📌 **팀 결정**
> - 진척 상황과 Task 배정은 **Jira**로 관리한다
> - 1차에서는 GitHub Issue를 사용하지 않았으나, 2차부터 **Jira 이슈마다 대응하는 GitHub Issue**를 추가로 등록한다
> - PR 본문에 `Closes #번호`를 적어 이슈와 해결 내역을 연결한다

## 코드 검증

- 중간 평가 시점의 Line Coverage는 **50%**, 기말 평가에서는 **70%** 이상이어야 한다
- 블럭 생성 확률을 검증하는 단위 테스트가 있어야 한다

> 📌 **팀 결정**
> 아이템 효과와 애니메이션 상태는 모델에서 처리하므로, 화면 없이 단위 테스트로 검증한다.

## 기타 주의사항

- 1차 요구사항과 마찬가지로 세부 요구사항은 팀별로 결정하며, 필요한 경우에만 문의한다
- 기능적·비기능적 요구는 섞여서 제시될 수 있으며, **암시적으로 요구되는 사항**도 평가 시 확인할 수 있다
- 강의 시간에 배우는 내용들을 잘 적용할 것
