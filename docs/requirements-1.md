# 세부 요구사항

## 시작 메뉴

게임 실행 시 처음 나오는 화면.

- 메뉴 화면 **상단에 게임 이름 표시**

> 📌 **팀 결정**
> 게임 이름을 **아스키 아트**로 표현하는 방안을 고려한다. 적용 결과에 따라 변경될 수 있다.

- 게임 이름 아래에 **시작 / 설정 / 스코어보드 / 게임(프로그램) 종료** 메뉴 표시
  - 각 메뉴를 선택하면 해당 기능이 수행되어야 한다
- 메뉴 사이 이동은 **키보드**로 가능해야 한다
- 선택은 **엔터 키**
- 그 외 키 입력 시 화면에 **사용 가능한 키를 표시**
- 메뉴는 이후 확장될 가능성이 있다

> 📌 **팀 결정**
> 메뉴를 **리스트 형식**으로 설계하는 방안을 고려한다. 적용 결과에 따라 변경될 수 있다.

## 테트리스 게임

시작 메뉴에서 게임 시작을 선택하면 테트리스 게임이 시작된다.

### 기본 구성

- **20줄 × 10칸**의 보드
- 테트라미노 **7종류**가 무작위로 등장
- 블럭으로 각 행을 전부 채우면 해당 행이 삭제됨

> 자세한 게임 방식은 실제 테트리스 게임을 참고할 수 있다.

### 화면 구성

기본적으로 다음을 포함한다.

| 영역 | 내용 |
|---|---|
| **보드** | 블럭이 쌓이는 곳. 20줄 × 10칸 |
| **다음 블럭** | 각 블럭이 보드에 생성될 때 다음 블럭을 표시 |
| **점수** | 실시간으로 반영 |

> 📌 **팀 결정**
> 다음 블럭들을 **큐 형태로 저장**하여, 화면에 여러 개를 표시할 수 있도록 확장 가능성을 확보한다.

### 게임 조작

- 블럭 생성 시 조작과 무관하게 **1초에 1칸씩** 아래로 떨어진다
  - 일정 수 이상 블럭이 생성되거나 줄이 삭제되면 **떨어지는 속도가 증가**한다
- 키보드 입력에 따른 조작
  - 좌 / 우 / 아래로 한 칸씩 이동
  - **시계방향으로 90도씩** 회전
  - 한 번에 끝까지 아래로 떨어뜨리기
- 모든 키 입력은 **씹히는 일 없이 즉시 정확하게** 반응해야 한다
- 게임 도중 **일시정지 / 재개** 키가 존재해야 한다

> 📌 **팀 결정**
>
> **속도**
> 블럭 속도에 **레벨제**를 도입한다. 제거한 줄 수와 생성한 블럭 개수를 종합한 수치로 속도를 결정한다.
>
> **키 설정**
> - 게임 도중 일시정지 키를 두고, 일시정지 화면에 **게임 종료 등을 포함한 옵션**을 표시한다
>
> **회전**
> 각 블럭의 **회전 상태를 미리 정의**하는 방식으로 구현한다.
> 이후 실제 표준 조작법으로 교체·확장 가능하도록 설계한다.
> (실제 표준 동작은 블럭마다 중앙 칸 또는 칸 경계를 중심으로 회전)
>
> **충돌 판정**
> 회전 시 블럭이 겹치는 경우 **좌우 1칸씩 옮겨서 재시도**하고, 실패하면 회전을 취소한다.
> 역시 이후 실제 표준으로 확장 가능하도록 설계한다.
> (실제 표준은 블럭마다 5개 정도의 오프셋이 미리 정의되어 있음)

## 블럭 종류

- 테트리스의 **7가지 블럭** 구현 (참조 코드 있음)
- 다음 블럭은 동일 확률로 무작위로 결정
- 각각의 블럭은 모두 다른 색상을 가지고, **색상 및 무늬로 구분** 가능해야 한다 (특히 유사 블럭 구분이 용이하도록)

> 📌 **팀 결정**
> 기본 블럭 색은 **세계 표준**을 준수한다.

---

## 색맹 모드

- 색각이상자가 색으로 인한 구분에서 불리하지 않도록 **색약 모드**를 지원한다
- 모드 선택 시 적녹색맹 및 청황색맹 등에서 블럭 구분이 쉽도록 색을 변경한다

> 📌 **팀 결정**
> - 블럭 종류별로 **색깔뿐 아니라 표현 텍스트에도 차이**를 부여한다
> - 옵션에서 **토글 방식**으로 변경하며, 변경 시 팔레트에 적용한다

---

## 점수 계산

- 블럭이 **1칸 떨어질 때마다** 단위 점수 획득 (조작 무관)
- 바뀐 점수는 **실시간으로 표시**
- 블럭 속도가 더 빨라지면 점수 추가 획득
- 그 외 점수 가산 방식을 **1가지 이상 추가 구현** (형태는 자유)

> 📌 **팀 결정**
>
> **줄 삭제 점수**
> 한 번에 지우는 줄 수에 따라 차등 부여한다.
>
> | 줄 수 | 점수 |
> |---|---|
> | 1줄 | 100 |
> | 2줄 | 300 |
> | 3줄 | 600 |
> | 4줄 | 1000 |
>
> **백투백 시스템**
> 4줄 동시 제거를 **연속 2번** 성공하면 점수 2배. 연속 백투백 가능
>
> **레벨 반영**
> 점수 가산에도 레벨제를 반영한다 — 현재 레벨을 점수에 **배율로 가산**한다.

## 설정 화면

설정 화면에서 제공해야 할 기능.

- 게임 화면 크기 조절 (**최소 3가지 이상**)
- 게임 조작 키 설정
- 스코어보드 기록 초기화
- 색맹 모드 설정
- 모든 설정 초기화

변경한 설정은 **저장 후 불러오기**가 가능해야 한다. 그 외 설정 추가는 자유.

> 📌 **팀 결정**
> - **시작 메뉴와 일시정지 화면 양쪽**에서 설정에 접근 가능하도록 구현한다
>   - 단 **스코어보드 초기화는 일시정지 설정 화면에서 제외**한다
> - 설정은 **properties 파일** 형식으로 저장한다
> - 설정 항목의 추가 확장을 고려하여 시작 메뉴와 유사하게 구성한다

## 게임 종료

- 블럭을 **더 쌓을 수 없는 상태**에서 게임 종료
- 게임 종료 시 스코어보드 표시
  - 스코어를 기록할 필요가 있는 경우 **이름 입력 화면** 표시
  - 이름 입력 후 스코어보드 업데이트, **직전에 입력된 이름과 점수를 강조 표시**
- 종료 처리가 끝나면 메인 메뉴로 돌아가거나 게임 종료

> 📌 **팀 결정**
> - 스코어보드 표시 위치는 **대략적인 구현 후 결정**한다
> - 처리 순서를 **스코어보드 표시 → 스코어보드 업데이트 → 종료 행동 선택**으로 구분하여 구현한다
> - 게임 종료 판정 기준은 **생성 위치에 블럭 생성이 불가능한 경우**로 한다 (표준 방식)

---

## 스코어보드

- 점수 순위를 보여주는 스코어보드 구현
- 순위별로 이름 및 점수 등을 **점수가 높은 순으로 정렬**
- 전체 기록 순위는 **최소 상위 10개**
- 설정에서 초기화 가능하며, 초기화 이전에는 프로그램이 종료되어도 기록을 유지해야 한다
- 그 외 사항은 자유

> 📌 **팀 결정**
> - 스코어보드는 **CSV 형태**로 저장한다
> - 한 화면에는 **10개**를 표시한다
> - 확장하여 표현하는 경우 **좌우 버튼으로 페이지처럼 넘길 수 있도록** 구현한다

## 추가 세부사항

> 기본 요구사항을 만족한 후 구현을 고려한다.

### 고스트 피스

현재 블럭이 떨어질 위치를 미리 표시한다. (즉시 낙하를 입력했을 때 블럭이 떨어질 위치와 같다)

### 홀드 기능

블럭 하나를 임시로 보유하여 필요할 때 자유롭게 바꿀 수 있는 기능.

- 기본적으로 홀드 칸은 비어 있다
- 홀드 버튼 선택 시 현재 표시된 블럭을 즉시 홀드 칸에 저장한다
- 홀드 칸이 채워져 있는 경우, 현재 블럭과 기존 블럭을 교체하여 다시 낙하시킨다
- 교체되어 나온 블럭은 **바닥에 고정될 때까지** 다시 홀드할 수 없다

## 프로젝트 관리

- 코드는 **VCS**를 통해 관리
- 프로젝트 진행 중 발생한 **이슈와 해결 상황**을 적절히 기록·관리
- **팀원별 업무 분담**을 적절히 기록·관리
- 위 산출물들을 관리하고 중간·최종 결과물로 제시할 수 있어야 한다

> 📌 **팀 결정**
> - **코드는 GitHub**, **이슈 관리는 Jira**를 도입한다
> - 브랜치는 `dev`를 기본으로 운영하고, 제출 시점에 `main`으로 병합한다
> - 회의록 등 문서는 GitHub 저장소에서 함께 관리한다

## 코드 검증

- 작성된 코드를 검증할 수 있는 **단위 테스트**를 충분히 작성해야 한다
  - **직접 작성한 코드** 기준 Line Coverage **50~70% 이상**
- 비기능적 요구사항 충족 여부를 검증하는 테스트가 **1개 이상** 존재해야 한다
- 테스트도 코드와 마찬가지로 관리 가능해야 한다
- 변경사항 발생 시마다 테스트를 간단히 실행하여 검증할 수 있는 체계를 갖춰야 한다

> 📌 **팀 결정**
> Unit test framework를 사용하고 code coverage를 지속적으로 관리한다.

## 게임 실행 및 배포

- 작성된 코드 및 필요한 정보로 **패키징이 간단하게** 이루어질 수 있어야 한다
- 배포용 패키지에는 **아이콘이 포함된 실행파일**이 있어야 한다
  - 실행파일을 더블클릭하는 등 **운영체제 동작으로 실행** 가능해야 한다
  - 명령어 입력이 필요하지 않아야 한다
- 대상 운영체제는 위 조건 중 하나여도 무방하다
- Java 21 버전 이상의 설치 및 사용 환경은 미리 갖추어져 있다고 전제해도 된다
  - 또는 JRE 자체를 패키지에 포함하는 방법도 가능하다

## 기타 주의사항

- 위 요구사항들은 대략적인 부분이며, **세부사항은 팀별로 분석하여 결정**한다
  - 모호한 부분이나 팀 내에서 결정하면 문제가 될 부분만 별도로 문의한다
- 슬라이드 요구사항에는 **기능적·비기능적 요구사항이 섞여서** 제시될 수 있다
- 명시되어 있지 않은 **암묵적인 요구사항**도 평가에 반영될 수 있다
- 강의 시간에 배우는 내용들을 잘 적용할 것

> 📌 **팀 결정**
> 알고리즘의 경우, 참조할 수 있는 오픈소스 코드 등이 있다면 구현에 도움이 될 것으로 보인다.
