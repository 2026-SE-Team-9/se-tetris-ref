## 결정 사항

### 역할 분담

계층을 기준으로 세 역할로 나누되, 모델 영역은 필요 시 파일 단위로 나누어 협업한다.

| 역할 | 담당 영역 |
|---|---|
| **게임 로직** | 보드 상태, 블록 낙하·이동·회전·충돌, 줄 삭제, 점수 계산 |
| **시각화 / UI** | 시작 메뉴, 인게임 렌더링, 설정 화면, 스코어보드, 색맹 모드, 화면 크기 |
| **조작 / 빌드** | 키 입력 처리, 키 설정, 설정·점수 파일 저장, 빌드·배포·테스트 자동화 |

- 빌드·테스트·배포 등 인프라 작업은 **조작 담당이 겸한다.** 세 역할 중 어디에도 속하지 않아 누락되기 쉬운 영역이라 담당을 명시했다.
- 실제 작업 배분은 **이슈 단위로 조정**하며, 역할은 기본값으로만 둔다.

### 역할 분담 방식의 근거

최초 분담안으로는 기능 축(게임플레이 / 메뉴·설정 / 스코어보드)으로 나누는 안도 검토했으나, 계층 축을 선택했다.

- 기능 축은 공용 클래스(`Board`, `GameState` 등)를 여러 명이 동시에 수정하게 되어 충돌이 잦다
- 한 사람이 화면과 로직을 함께 작성하면 계층이 섞여 단위 테스트가 어려워지고, 커버리지 요건 달성이 힘들어진다
